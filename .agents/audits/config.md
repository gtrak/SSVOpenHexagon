## DIFFERENT

Present but renamed or behaviorally different:

1. **JSON type-coercion strictness (governs persistence of all 101 keys + combo arrays).** The vendored jsoncpp fork coerces across types: `asBool` accepts int/uint/real (`jsoncpp.inl:1310-1322`), `asInt`/`asUInt` accept bool and real (:1191-1227), `asFloat`/`asDouble` accept bool (:1284-1309), `asString` accepts bool/int/uint/real (:1177-1189). Rust `oh_data::json::as_bool/as_int/as_float/as_str` reject every non-matching type with `JsonError` (`crates/oh-data/src/json.rs:336-381`). Consequences for a user-edited `config.json`: `"vsync": 1` → C++ loads (`true`), Rust `load_config` errors → app exit (per seam #5); `"music_speed_mult": true` → C++ 1.0, Rust error; a numeric element inside a trigger combo array → C++ `Converter<Combo>::fromObj` coerces `123`→`"123"`, invalid name → warning + unbound combo (`UtilsJson.cpp:91-124`), Rust `Combo::from_obj` hard-errors (`triggers.rs` `Combo::from_obj`, `json::as_str(item)?`). Root cause lives in `oh-data/src/json.rs` (separate audit lane) but it is this module's persistence behavior. Risk: **data-format**.
2. **`loadConfig` re-read semantics.** C++ `root()` is a function-local static: `config.json` is read once per process; a second `loadConfig` re-merges overrides into the already-loaded root without touching the file (`Config.cpp:376-394`). Rust `load_config` re-reads `config.json` from disk on every call (`config.rs:594-655`). In practice C++ calls `loadConfig` once per process (`main.cpp:201` server / `:282` client), so the difference only surfaces on double-load with a file modified in between (which the Rust test does: `tests/config_release.rs:312`). Risk: none.
3. **`getKKeyName(Unknown)`** — C++ asserts (`SSVStart/Utils/Input.hpp:192-196`; release build would read out of bounds); Rust returns `""` (`triggers.rs` `get_kkey_name`, documented: "the port returns `""` for `Unknown` instead of tripping the debug assert"). Practically unreachable: bit 0 set ⇒ combo `isUnbound()` ⇒ `getKeyboardBindNames` breaks before naming it. Risk: none.
4. **`getTrigger(Unknown/TriggersCount)`** — C++ indexes `triggerGetters` out of bounds (UB, `Config.cpp:1636-1638`); Rust panics with `bad Tid` (`config.rs:1883-1907`, `:1931-1945`). Same intent, defined failure instead of UB. Risk: none.
5. **Rename map (no behavior change)** — `getX`→`get_x`, `setX`→`set_x` (incl. `get3D`→`get_3d`, `getMaxFPS`→`get_max_fps`), `maxBinds`→`MAX_BINDS`, `defaultSpawnDistance`→`DEFAULT_SPAWN_DISTANCE` (private), `triggerGetters[]`→`get_trigger`/`trigger_ref`/`trigger_copy`, `joystickTriggerGetters[]`→`joystick_bind(Jid)`, `joystickTriggerSetters[]`→`set_joystick_bind_value(Jid, u32)`, `uppercasify`→`to_ascii_uppercase` (ASCII-identical for this vocabulary), free functions over statics → `Config` struct (architectural, documented in `config.rs` module doc). Verified mechanically: 81/81 getters and 57/57 setters map one-to-one; 101/101 keys in identical order with identical JSON names and defaults; 174/174 whitelist ids verbatim; trigger/joystick defaults identical.

## VERDICT

**FAIL (not 1:1 yet).** The single most important gap: C++ `resetConfigToDefaults()` (triggered by the menu "RESET CONFIG", `MenuGame.cpp:1165-1177`) resets **all 101** `LinkedValue`s — `resetAllFromDefault()` iterates the full `X_LINKEDVALUES` macro whose last line is `X_LINKEDVALUES_BINDS` (`Config.cpp:373, 455-460, 538-544`) — but Rust `reset_config_to_defaults` (`crates/oh-config/src/config.rs:919-994`) resets only the 73 non-bind values and leaves every custom keyboard/joystick bind in place; it also omits the trailing `reapplyResolution()`/`recalculateSizes()` (`Config.cpp:535`) with no `recalculate_sizes` caller anywhere in the Rust tree. A user who hits "RESET CONFIG" in the Rust build keeps their custom key binds (gameplay-relevant) and stale `sizeX/sizeY/zoomFactor`, while the C++ build restores both.
