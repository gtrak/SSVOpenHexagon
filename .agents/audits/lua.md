## DIFFERENT

Present but renamed or behaviorally different:

1. **Out-of-range color-channel conversion in `cw_setVertexColor*`.** C++ builds `sf::Color(r, g, b, a)` from the Lua `int` args — channels are `unsigned char`, so out-of-range values **wrap modulo 256** (`LuaScripting.cpp:326, 374, 405`): `300 → 44`, `-1 → 255`. Rust does three different things: `cw_setVertexColor` uses `u8::try_from(x).unwrap_or(255)` (`custom_walls.rs:141-144`: `300 → 255`, `-1 → 255`), while `cw_setVertexColor4`/`cw_setVertexColor4Same` use the `color()` helper's `v.clamp(0, 255)` (`custom_walls.rs:391-392`: `300 → 255`, `-1 → 0`). So Rust is internally inconsistent *and* differs from C++ for every out-of-range channel (in-range behavior is identical; in-range is the only case sane pack scripts use). C++ evidence: `LuaScripting.cpp:320-327, 366-381, 400-405`; Rust: `custom_walls.rs:137-149, 391-395`. Risk: **uservisible-cosmetic**.
2. **Wrong comment on `s_getColor` (behavior itself is correct).** `style_control.rs:398-401` claims "C++ `StyleData::getColor(index)` uses `std::vector::at` (throws out-of-range); the port surfaces the same failure as a Lua runtime error" — that is false: C++ wraps cyclically, `StyleData.cpp:320-323` (`ssvu::getByModIdx`, `Containers.hpp:274-277`), exactly like the Rust `get_color` (`oh-data/src/style_data.rs:349-353`, `m_idx % len`, negative `i32 → u32` wrap included). Consequently the `ok_or(LuaError …)` error branch at `style_control.rs:401-404` is **dead code** (`get_color` only returns `None` when `current_colors` is empty, which the `:394` guard already handles). The `$N`/index wrap behavior is 1:1; the comment and the unreachable error arm are the defect. Risk: none (documentation drift; no behavioral difference).
