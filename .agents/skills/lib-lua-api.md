# lib-lua-api — the `oh-lua` game API (issue 007)

The complete Lua game API registered over `LuaContext` (`crates/oh-lua/src/api/`):
285 registered global function names (game context) plus the menu-context
overrides. Authority: `src/SSVOpenHexagon/Core/{LuaScripting,HGScripting,MenuGame}.cpp`
+ `.agents/plans/001-rust-port/mapping/lua-api.md` (§1/§2 name set, §3
conversion, §5 callbacks, §8 subtleties).

## Registration entry points (`api/mod.rs`)

- `init_lua_api(ctx, state)` — C++ `LuaScripting::init` (shared by game and
  menu): `random` → `redefine_io_open`/`redefine_random`/
  `destroy_malicious_functions` → `utils` → `custom_walls` → `level_control`
  → `style_control` → `exec_script` → `shaders` → `config`.
- `init_level_api(ctx, state)` — C++ `HexagonGame::initLua` groups, in order:
  `level_utils` → `audio` → `main_timeline` → `event_timeline` →
  `custom_timelines` → `level_control_level` → `style_level` →
  `wall_creation` → `steam` → `deprecated` (incl. the `m_*` aliases).
- `init_menu_api(ctx, state)` — shared init with `in_menu == true`, then
  `menu::register`: the `u_log` override, the 4 pinned constant getters
  (`u_getDifficultyMult`/`u_getSpeedMultDM`/`u_getDelayMultDM` → 1,
  `u_getPlayerAngle` → 0), and the 71-entry no-op "unused functions" list
  (verbatim, incl. historical `u_timelineWait` and the duplicated
  `u_setFlashEffect`). The menu context therefore does NOT contain the four
  game-only globals `l_forceSetPulse`, `l_forceSetBeatPulse`,
  `u_impl_addTrackedResult`, `u_swapPlayer`, and DOES contain
  `u_timelineWait` (C++ writes it in the no-op loop).
- Name-set invariant: game context registers exactly 285 globals
  (135 `addLuaFn` + 72 `makeLuaAccessor` vars × 2 + 5 `sdColorGetter` + 1 raw
  `u_impl_addTrackedResult`); enforced by `tests/api.rs::registered_name_set_matches_source`.

## `add_lua_fn!` — spread-argument registration (the issue-007 core)

C++ `FunctionToPush` invokes the callable with its N parameters as N
SEPARATE stack values (spread), never as one tuple. Stable Rust cannot name
a generic `Fn(A, B, …)` for variable N in a trait bound (coherence: the
arity is not a type), so `oh-lua` provides one concrete method per arity,
`add_lua_fn_0` … `add_lua_fn_17` (and the `_raw_` variants without
metadata), generated by `impl_lua_fn_arity!` in `context.rs`; the
`#[macro_export]` macros dispatch by matching the closure's parameter count:

```rust
oh_lua::add_lua_fn!(ctx,
    "l_setSpeedMult",
    oh_lua::FnMeta { ret: "void", arg_types: &["float"] },
    move |value: f32| { lock(&st).level_status.speed_mult = value; },
)?
.arg("value")
.doc("Sets the speed multiplier of the level to `$0`.");

// raw (no metadata — C++ `lua.writeVariable`):
oh_lua::add_lua_fn_raw!(ctx, "u_impl_addTrackedResult", move |result: String| { … });
```

- The macro accepts `|a: T, b: U| …` (or `move |…|`) with explicit
  parameter types, arities 0–17 (the game's largest signature is
  `cw_setVertexColor4`, 17 parameters). `FnMeta::arg_types` must list one
  `typeToStr` spelling per parameter (debug-asserted at registration).
- `add_lua_fn_try!` is an alias for `add_lua_fn!` — a fallible closure
  (`|a: i32| -> Result<(), LuaError>`) routes through `FnReturn for
  Result<T, LuaError>` and surfaces its error as a C++ `std::runtime_error`
  Lua runtime error.
- Closure bodies must not take a tuple argument: `move |_t| { let (a, b) = _t; … }`
  is the OLD (issue-006) shape and no longer compiles against the API.
- The returned `LuaMetadataProxy` records the docs entry on drop (C++
  `~LuaMetadataProxy`); `.arg(name)` per parameter, `.doc(text)` with `$N`
  placeholders.

### Exact C++ call semantics (`context.rs::read_call_window`)

For a registered N-argument function, with `argc` Lua values passed:

- `argc < N - 1` → runtime error
  `"this function requires at least N parameter(s)"`.
- `argc == N - 1` → the C++ last-slot read lands on the callee itself
  (userdata) → `"Trying to cast a lua variable to an invalid type"`.
- `argc >= N` → the LAST N values are read (extras dropped from the front);
  `N == 0` reads nothing. Per-value coercion follows `FromLuaValue`
  (nil-coercion table, mapping §3/§7.3; userdata → the cast error above).

These are NOT ordinary Lua arity checks — they mirror
`Utils/LuaWrapper.hpp::FunctionToPush` verbatim; see
`tests/api.rs::registered_fn_arity_mismatch_and_window` and
`tests/runtime.rs::registered_fn_arity_and_arg_window`.

## State interface (`api/state.rs`)

- `GameApiState` — field-for-field mirror of the C++ `HexagonGame`/
  `LuaScripting` captured state; `GameApiState::new(…)` (14 args,
  C++-initial values) — the engine (issue 009) implements the two traits
  below.
- `AssetsApi` — the `HGAssets` lookups (music/style/pack/shader data +
  uniform setters). `GameApi` — the engine operations (config, input,
  audio, messages, death, walls, pulse, camera, steam, `go_to_menu`). Both
  `Send + Sync`; tests use recording mocks (`tests/api.rs`).
- `State = Arc<Mutex<GameApiState>>`; every registered closure locks it via
  the module-private `lock()` (poisoned lock is recovered — C++ has no
  poisoning). Deferred timeline actions clone the `Arc` (`let st2 = st.clone();`)
  before the inner `move` closure, because the registered closure is `Fn`
  (shared) and may not move its capture.
- `SharedLua` — a `'static`-extended `&LuaContext` (raw pointer,
  `Send + Sync` by explicit contract): the context must outlive every
  closure/action holding it (single-thread Lua usage).
- `RunLuaFile = Arc<dyn Fn(&str, &SharedLua) -> Result<(), LuaError> + Send + Sync>`.

## Accessors

`level_control.rs::reg_accessor!` / `style_control.rs::reg_style_accessor!`
register the `makeLuaAccessor` get/set pair for one struct field:

```rust
reg_accessor!(ctx, state, "SpeedMult", f32, "float",
    |s: &mut GameApiState| s.level_status.speed_mult,
    |s: &mut GameApiState, v| s.level_status.speed_mult = v,
    "Gets the speed multiplier of the level. …",
    "Sets the speed multiplier of the level to `$0`. …");
```

The macro clones `state` per registration (the call site must pass `state`,
not a shared `st` local, because each registration `move`s its clone) and
hoists the clone outside both closures (block-bodied closures do not match
the `add_lua_fn!` patterns). Getter/setter closures take
`s: &mut GameApiState` (explicit annotation required — the macro cannot
infer it).

## Deprecated/aliased functions

`deprecated.rs` registers the C++ `initLua_Deprecated` aliases (`u_kill` →
`e_kill`, `m_*` → `e_*`, …). The C++ lambdas first call
`_checkDeprecatedFunction(name)`, which logs
`"Deprecated function '<name>' called\n"` to the `Deprecation` channel the
first time per name (`state.called_deprecated_functions`) — `raise_warning`
in `deprecated.rs` reproduces the exact C++ message; it must NOT be dropped
(or replaced by a Rust-style warning) when the alias bodies are edited.
